03 · 三根支柱 / Pillars Design · Build · Optimize

造软件拆成三件事，进度极不均衡

要把 Agent 用于基础软件构建，Niko 认为应该拆成三根支柱。没有一件被真正解决。

DESIGN · 设计
想清楚，并且明确规格化
这段代码到底该做什么。当前最先进的做法，基本还停在「写 Markdown，然后指望 Agent 认真读」。
现状：文档 + 提示词
进展最慢
BUILD · 构建
写出确实做了该做的事的代码
可靠性次之：类型系统已经提供了一部分现成的护栏，但护栏之外还有大片空白。
现状：类型检查 + 测试
有现成护栏
OPTIMIZE · 优化
把代码调到高效运行
进展最快，因为性能有明确的客观信号可用：跑一次 benchmark，好坏立刻分晓。
现状：benchmark + profiler
信号最清楚
这个进度差异决定了全文的重心。
为什么 Rust 在优化和可靠性上有优势，为什么设计才是真正难啃的骨头。
「三件事里，只有一件能靠工具给答案。」
三件事没有一件被真正解决，但只有优化手里握着一把客观的尺子。
优化跑得最快，设计几乎没动，后面两幕由此展开。 Design / Build / Optimize
04 · 性能 / Perf Rust 2026

默认就快，还能一处处拧

旋钮一直在，只是过去要多年经验才敢碰。Agent 改变了谁能碰它们。

P1
默认性能就好
惯用的写法通常也是最快的写法，不写优化也能拿到不错的代码，这是 Rust 性能哲学的第一句。
P2
旋钮全都留着
栈还是堆、指针间接在哪、结构体布局怎么排、async 帧在哪装箱，极限情况还能写内联汇编。过去掌握这些近乎玄学。
P3
Agent 很会拧
高性能密码学圈子过去靠人手工调汇编，现在把这份活交给 Agent；做网络服务的人用 dial9 这类 profiler，让 Agent 去诊断 long poll、阻塞这类 async 陷阱。
代码→ benchmark→ profile→ Agent 分析→ 提出 PR→ 代码变快↺
PROFILER + AGENT
这条回路一旦转起来，性能会持续复利，而不是一次性的手工调优。
过去旋钮属于少数人的经验，调优近乎玄学，只有多年积累的人敢碰。
现在profiler 把经验变成可读的信号，Agent 负责一遍遍动手去调。
profiler 加 Agent，把性能优化变成一条会复利的回路。 Dial9 / Benchmark Loop
幕间 / Interlude Quote

Rust 是完美的 Agent 语言，
因为只要它能编译，
就约等于正确。

Greg Brockman 在 2026 年 1 月这么说。这个判断并非 Rust 独有，OCaml 和 Haskell 也共享同一种「编译即正确」的手感，而 Agent 恰好最能从这种手感中获益。

但这句话是个伏笔 能编译就正确只是一道强护栏，它不是正确性证明。下一部分会论证，为什么它既不够用，又不可替代。
强护栏值得押注，但别把它当成证明。 Greg Brockman · 2026-01
05 · 测试 / Tests Correctness

测试能显示缺陷存在，不能显示它不存在

Dijkstra 1970 年的那句话，在 Agent 写代码之后更成立，差得不是一星半点。

T1
头几个测试都挺好
跑通、覆盖、看起来都符合预期，于是你开始信任这段代码。
T2
再写一个，就彻底发疯
疯到你根本想象不出这个 bug 是怎么来的，复现路径看着毫无道理。
T3
挖下去才发现
Agent 完全跑偏了你试图表达的逻辑。测试没写错，是你表达的东西根本没被实现。
T4
护栏从类型系统来
尤其是 Rust 这种进阶类型系统：不止查字段名，还能给出资源安全保证，把一整类生命周期错误从可能变成不可能。
歪掉的蛋糕配一句 Nailed it，就是 Agent 展示成果的样子。
测试写得再多，也证明不了缺陷不存在。 Dijkstra · 1970
06 · 类型 / Types Proof Tools

类型系统能显示缺陷的不存在，但不能显示正确性的存在

Niko 仿 Dijkstra 造了这个句子。它只是一组简单的规则，遵守它就避开某几类错误。

它只保证你没做错某些事，不保证你做对了事。想再进一步，就需要证明系统，去展示更丰富的性质确实成立。
Verus
借助借用检查器来简化 SMT 求解，让求解器少处理一大块约束。
借用检查 / SMT
Creusot
走演绎验证的路线，把 Rust 代码生成成 Why3 目标。
演绎验证 / WHY3
Aeneas
把 Rust 翻译进证明助手，在证明助手里完成剩下的推理。
翻译 / 证明助手
Kani
用模型检查覆盖 panic 自由这类性质，不需要人手写证明脚本。
模型检查 / PANIC-FREE
第一步 · 先证明代码 PANIC-FREE消掉一大批 bug。虽然本质上还是「避免做错」的类型检查式性质，但门槛低、收益大。
第二步 · 再往上加断言证明代码算出来的正是你想要的结果，这时候才真正触到「正确」。
这几条路径的共同点：先用便宜的类型检查白拿一批正确性，再把证明的力气花在真正要紧的性质上。
证明系统往前推一步，但只该用在真正重要的性质上。 Verus / Creusot / Aeneas / Kani
07 · 证明 / Proof Unsafe & Perf

部署证明，不只为了写对，也为了写快

全篇最反直觉的论点：密码学算法有极清晰的数学定义，于是可以换一种方式指挥 Agent。

PR
定理证明器接活
对 Agent 说：随便你怎么写，只要能证明结果依然正确。Lean、Rocq 这类定理证明器能承担这份工作，《Why Lean is faster than Rust》把这个思路演示得很漂亮。
UF
最有价值的落点是 unsafe
现在很多人不愿上 unsafe，哪怕它更快，因为一旦错了，代价完全不值得。这个保守态度是合理的，问题在于它挡住了整条优化路径。
BD
证明之后，才敢优化到底
如果能证明这段 unsafe 代码不会触发未定义行为，就可以放心压榨性能，而不是靠祈祷和代码评审。
BOUNDARY / 一条不能松的边界
安全 API 必须保护使用者，无论他怎么滥用。Rust 在这一点上态度明确，而 C++ 经常把未定义行为的责任推回给用户。
证明在这里不是为了让人少写代码，而是让 Agent 敢往更危险、也更快的地方走。
能证明没有未定义行为，unsafe 才敢优化到底。 Lean / Rocq / Unsafe
08 · 分工 / Division Types vs Proof

有了证明系统，为什么还要类型系统

因为易用性。类型系统简单得多，所以流行得多，先把烦人的小 bug 排掉，才轮得到证明上场。

JAVA · 不看更多代码就证明不了
给字段赋值，再断言相等
在 Java 里写下这段逻辑，你无法证明断言成立，因为随时可能有别的线程在改 this。局部看起来没问题，全局却说不清。
想证明它，得先排除整个对象上所有并发的写入。
RUST · 断言必然成立
同样的逻辑，多一条保证
在 Rust 里，只要 Eq 对 Bar 自反，这个断言必然成立。原因在于类型系统保证了 &mut self 是一个唯一引用。
唯一性由借用检查器追踪，不需要证明器去猜。
证明同一个断言还需要什么条件结论
Java没有别的线程同时在写 this看局部代码看不出来
Rust只要 Eq 对 Bar 自反断言必然成立
这也正是 Verus 的工作方式。信任借用检查器来追踪唯一性，SMT 求解器需要处理的约束就小得多，证明检查因而更快、更可靠。
先用便宜的类型系统排掉小错，把宝贵的证明精力留给大事。 &mut self / SMT
09 · 下注 / Double Down Type System

在「编译即正确」上继续加倍下注

Rust 的类型系统已经很有表达力，但仍有一批它捕捉不到的东西，既有很常见的，也有很花哨的。

G1
常见的缺口
比如「这个方法只读某一个字段」的视图类型，以及内部引用这样的长期难题。它们不花哨，但天天在写。
G2
花哨的缺口
比如「不得记录个人可识别信息」这种合规性质。类型系统现在完全接不住，只能靠人盯。
G3
工程上的缺口
现有的 Rust 证明工具虽然酷，但使用过程很别扭，要应付一堆宏和钉死的编译器版本。这必须变成一套体面的流程，否则证明能力再强也推广不开。
方向
逐个抬高这些上限，给 Agent 留出证明更复杂性质的空间，而不是让它在类型系统外面绕路。
先补常见的缺口，再补花哨的性质，同时把证明工具做成普通编译流程的一部分。
缺口一个个补，证明工具链也得变成体面的流程。 View Types / PII
10 · 北极星 / North Star Unsafe

北极星：不再有 unsafe 代码

关键是别把 unsafe 理解成关键字。它指的是，对我们写下的每一段 unsafe 代码，我们都有能力证明它不会引发未定义行为。

A1
已有的进步必须承认
现在「到底哪些代码需要被审计」这件事清晰多了，不再是一笔糊涂账。
A2
也已经形成共识
库必须通过安全 API 边界，保护用户免于未定义行为。
A3
但标准还得再抬一档
面对 Agent 挖掘漏洞的能力，旧标准挡不住源源不断的 CVE，证明能力必须跟上。
比喻的尺度 · CVE 的数量级
Rust：一条 CVE 溪流
有类型系统保护
C++ / Java：一场洪水
缺少同等保护
宽度为原文比喻的定性示意，非实测数值。
Rust 遇到的是一条溪流，C++ 和 Java 遇到的是一场洪水。 North Star / No Unsafe
11 · 设计 / Design Markdown Driven

三根柱子里最弱的一环：设计

在证明和优化之前，你得先清楚自己在造什么。而当前最先进的做法，基本就是 Markdown 驱动开发。

D1
接口从实现里拆出来
方便单独评审接口，或者一眼看出 Agent 在哪动了接口。这带着点当年头文件的复仇意味。
D2
至少提供更好的评审工具
让人的注意力落在真正变了的地方，而不是在巨大的 diff 里找线索。
D3
走出传统编程语言的范畴
做专用的建模语言，让人在高层设计与不变量上快速迭代，而不必扎进代码里。
D4
一本值得读的书
Kari Wilhelm 的《Principles of Anchor Engineering》，讲如何抽出设计的关键要素，并据此驱动编码。
开放问题
Niko 没有把握 Rust 在这个领域能占多大份额，但这是三根柱子里唯一还没有工具答案的一根。
设计还是 Markdown 加祈祷，这是最弱的一环。 Anchor Engineering
12 · 结论 / Summary Rust & Language Design

要做的事没变，变的是权衡的砝码

全篇收拢成两组结论：为什么 Rust 适配 agentic 开发，以及语言设计层面还能怎么更好。

为什么 Rust 适配
默认性能就好 惯用写法已经够快，何必多付钱。
profiler 随手可用 配上工具，想调多细就调多细。
类型系统是更强的护栏 配置得当，还能用 newtype 之类的技巧再加固。
Agent 极擅长微调性能 旋钮暴露得足够多，它就能一处一处往下拧。
语言设计还能怎么更好
加倍下注编译即正确 类型系统更能表达，别让 Agent 卡在绕开类型系统的死胡同里。
把北极星写清楚 unsafe 代码也无不安全，而不是笼统地说「减少 unsafe」。
守住光谱两端 低到能写内核，高到能写 GUI。该暴露的旋钮要暴露，意图要清晰，但不必把代码压到字符数最少。
继续发扬可扩展性 把宏加类型系统撑起的 DSL 精神带进编译器，覆盖 GPU、深度语言互操作，也接得上定理证明器这类非 token 工具。
总纲
要做的事和过去几乎一样，因为写代码的变成了 Agent，人类的精力转向了代码理解。
工具与语言都没换题目，只是每题的分值变了。 Two Sets of Conclusions
13 · 收尾 / Closing What's Easy Now

容易和困难，正在互换位置

Marc Brooker 的判断：一件事的成功标准越能被清晰规格化，它就越容易。

过去公认很难的任务，可能很快被自动化；
而过去觉得容易的任务，反而会变得更值钱。

NIKO 的接法
最大的动静将来自设计语言：一种让你在极高层捕获架构与意图行为的语言。人凭直觉写出设计，设计被翻译成有效的护栏，形式可以是类型检查、lint，也可以是待证明的定理；然后 Agent 负责把设计翻译成传统语言写的代码，人类只在偶尔看一眼。
传统语言的设计不会变得无趣，只是权衡的取舍和从前大不相同。
最大的动静，会来自一种让人直接写出设计的语言。 Marc Brooker / What's Easy Now
